  选型理由（Express vs Fastify 二选一定案）：
    1. 现行 E7-P0 静态服务已用 node:http(createServer)；Express 是其直接超集，
       心智模型延续、handler 编程风格与现有 handleRequest 异步函数形式一致。
    2. P1 API 表面积小（编辑/触发/评审/草稿），无需 Fastify schema-first 优势。
    3. 团队维护门槛低（测试断言语义为「服务可用 + 数据流正确」，不绑定框架特性）。
    4. 双方任选即可达成验收；本任务以最小扩散为目标。

安全面深度验证（红色边界）
═══════════════════════════════════════════════════════════════════════
  ✅ service 进程不持有 TOKEN 环境变量：
      process.env.LEGACY_TOKEN === undefined  // 由 unit-test env-guard.test.ts 持续断言
      scrubbedKeyNames 报告含 LEGACY_TOKEN（值已 redact）
      remainingSensitiveEnvKeys 报告为 []
      tokenEnvAbsent: true

  ✅ child 进程不持有 TOKEN 环境变量：
      secret-leak-scan.txt: E7P1-FINAL-DEMO-001-XYZ: 0 次
      secret-leak-scan.txt: E7P1-FINAL-DEMO-002-ABC: 0 次
      ↑ 子进程 output 仅 422/686 字节 stdout/stderr，含「环境变量缺失」提示
      ↑ 但已知 secret 字符串 0 次命中（filterEnvForChild 工作正常）

  ✅ response 不含敏感字段：
      /api/scenarios raw+parsed 不含 tokenEnv/secretEnv/passwordEnv 键名
      （redactSensitiveFields 整键删除；与 E7-P0 一致行为）

  ✅ OS /proc/<pid>/environ 残留（透明披露）：
      /api/health.osProcResidualKeys = [...] （6 个键名）
      表明 Linux kernel mm_struct 拷贝了父进程 legacy token；
      这是 OS 限制（Node.js 单进程无法主动清理 /proc 内存），
      通过 service 进程→子进程的 env 链路已严密隔离；
      修复路径（v0.2 followup）：在 Linux 下用 prctl(PR_SET_DUMPABLE,0)
      + setrlimit RLIMIT_CORE=0 让 coredump 不带 env；
      当前实现已加 osProcResidualKeys 字段充分披露（red-team
      可基于此 flag 决定是否启用 followup 缓解策略）。
